## Share Link Entry Contract (/s/{token}/)

来源：D-01/D-02/D-03（锁定）+ R-05（无效 token 页面形态）+ Open Question 1 用户裁决（token 通道与认证正交）。

- **URL 探测与提取**：`location.pathname` 匹配 **`^/s/([^/]+)/$`** 提取 token。无尾斜杠的 `/s/abc` 由服务端 301 补斜杠（GOROOT mux 内建行为），前端无需兼容；不匹配即走既有无 token 流程。
- **连接流程分支**：提取到 token → `fetch('/api/attach', { method: 'POST', body: JSON.stringify({ token }) })`（headers Content-Type: application/json）→ 后续 ticket → Hello 链路不变。mode 由 token 服务端绑定（ro token → ro ticket），**前端不解析、不分支 token 种类**——ro/rw 判定唯一来源是 Welcome.mode（既有纪律延伸）。
- **token 处理红线（T-03-24 泄漏面延伸，逐字纪律）**：token 只存 `connect()` 闭包变量与 POST body——禁止写入 console/localStorage/sessionStorage/任何日志调用；**禁止 `history.replaceState` 剥离 URL 中的 token**（D-03 路径段是分享/书签契约，且 1013 后手动刷新必须凭原 URL 重新 attach——剥离会使刷新落到无 token 流程，D-10 手动刷新入口失效）。
- **无认证模式（OQ1 裁决，token 通道正交）**：URL 携 token 时无认证模式同样走 fetch 分支（服务端 /api/attach 仅当 body 携 token 时非 404）；URL 无 token 时保持既有 404 探测 → 直连 WS 形态不变。
- **无效 token 双层响应（R-05 零新响应形态）**：
  1. **页面 GET 层**：无效/缺席 token → 服务端委托既有 `/` 处理链——凭据模式浏览器原生 Basic 框（P3 矩阵不变）；无认证模式直接给页（全站本无门）。**无自绘 error page**。
  2. **/api/attach POST 层**：携 token 401 → 前端**自知**本次请求携 token → 显示 §Copywriting C-3 "Invalid share link" 专版面（前端按自己发出的请求内容分派文案，不向攻击者泄露任何其本不知道的信息——无 oracle 纪律不约束前端侧文案）。
- **响应分派优先级（connect() fetch 分支完整矩阵，逐字契约）**：

| resp | 前置条件 | 动作 |
|------|----------|------|
| `ok` | — | `ticket = (await resp.json()).ticket`，继续 WS 链路 |
| `404` | — | 无认证模式探测信号（未携 token）：`ticket = undefined` 直连（既有形态不变） |
| `401` | 携 token | §Copywriting C-3 "Invalid share link"，return |
| `401` | 未携 token | 既有 "Authentication failed"（P3 文案不变），return |
| `429` | 任意 | 既有 "Too many attempts"（P3 文案不变；throttle 统一 per-IP 计数器 R-03），return |
| `503` | 任意 | §Copywriting C-2 "Server is full"（OQ2 裁决早闸），return |
| fetch throw | — | §Copywriting C-4 "Unable to connect"（改写后文案），return |

## Connection & Status Dispatch Contract

来源：D-10（1013 分派 + 手动刷新 + 不做自动重连）+ R-10（`slow_consumer` 机器串）+ RESEARCH Pattern 9（文案清扫）+ OQ2（503 早闸）。

- **onclose 按码分派结构不变**（P2 既定：只认 `ev.code` 不认 reason——**1013 的 close reason `slow_consumer` 是机器串，前端文案硬编码，永不渲染 reason 内容**；防伪造引导钓鱼，Security Domain 既定）。
- **1013 新增专版分支**：替换现状占位文案（"The server asked this client to retry later."），语义改为"因接收过慢被断开 + 会话无恙 + 手动刷新即接回最新输出"。文案逐字见 §Copywriting C-1。
- **手动刷新唯一入口（D-10 边界纪律）**：1013 分支**不做任何自动重连**（避免后台标签页重连→再被踢循环）；重连完整能力归 Phase 6 CORE-05。提示行 "Reload this page" 链接 = 既有 `location.reload()` 形态；URL 中 token 保留（上节红线）使刷新后可重新 attach。
- **beforeunload 既有联动不变**：onclose 任意路径移除 listener（含 1013 面板展示后）——终态面板下关页不再被拦截（04-UI-SPEC §Auxiliary Interactions 逐字有效）。
- **auth_failed 静默重试一次（P3 既定）不变**：携 token 流程同样适用——重试经 `connect()` 同一入口重新 POST 携 token。
- **fetch 阶段 503 早闸（OQ2）**：上节矩阵 C-2 分支。WS 握手阶段的 503（早闸后竞态窗口：ticket 已签但满员）前端**无法与网络失败区分**（浏览器不暴露 WS 握手状态码）——落 onerror/!opened onclose 通用文案 C-4，可接受（OQ2 裁决注记）。

## RO Mode & Promotion Contract

来源：D-06/D-07（owner 递补与降级形态）+ D-09（ro 不发 RESIZE）+ R-09（升格复用 'W' Welcome）+ RESEARCH Pattern 9（前端升格处理）。

- **ro 形态唯一来源 = Welcome.mode**：两种新场景复用同一既有形态，前端**不加区分**——(a) /s/{ro_token}/ 旁观者（ro ticket，永不递补）；(b) owner 在位时 rw 降级的递补者（rwEligible，将来了升格）。判定差异纯服务端语义，前端零感知。
- **ro 形态三要素（既有，逐字沿用）**：`term.options.disableStdin = true`（键盘层面不产生 onData，UX 层；真边界在服务端丢 INPUT）+ `[ro] ` 标题前缀（经 04-UI-SPEC §Title Sync Contract 单一写口）+ 不发 RESIZE（见下）。
- **ro 不发 RESIZE（D-09 第一闸，新契约行）**：`sendResize` 在既有 `!helloSent` 门之后、`readyState` 检查之前加 **`if (isRO) return`** 门。Hello 携首尺寸不受影响（helloSent 门先于 isRO 生效——isRO 仅在 WELCOME 到达后才可能为 true）。服务端忽略 ro RESIZE 为兜底第二闸（非本契约范围）。
- **升格处理（WELCOME 分支新增 rw 路径，逐字行为契约）**：运行期收到 `mode === 'rw'` 的 Welcome 时：
  1. `isRO = false; term.options.disableStdin = false;`
  2. `setTitle()`——经单一写口去 `[ro] ` 前缀（remoteTitle 不含前缀，04 契约既定）；
  3. `fit.fit()`——触发既有 onResize→sendResize 链路（isRO 门已开），自动向服务端上报当前尺寸（owner 尺寸接管的前端半侧；排队期间窗口可能已变）；
  4. prefs 应用段照常执行（升格 Welcome 携 rw 档 prefs，含 osc52——D-13；queryKeys 跳过机制幂等，xterm 键/behavior 键/theme 重放同值无害）；
  5. `beforeunload` 条件重注册——`addEventListener` 同参重复注册 DOM 规范去重，幂等无泄漏（RESEARCH Pattern 9 核实）。
- **升格信号 = 标题前缀消失 + 键盘激活，无通知组件（D-07 零新 UI）**：不加 toast/面板/badge；终端工具的最小铬哲学——用户发现自己能打字即升格完成。
- **降级不发生**：运行期不存在 rw→ro 反向翻转（owner 只在位到断线）；前端不实现降级路径。
- **剪贴板联动（自动生效，零新代码）**：Ctrl+Shift+V 粘贴门的 `isRO` 检查随升格翻转自动放行（04-UI-SPEC §Clipboard Contract 不变）；选中即复制 ro 下本就生效（旁观者可复制输出），不变。

## OSC52 Boundary (D-13)

- **服务端职责（非本契约范围，登记边界）**：prefs 按客户端 mode 分化双档 blob——ro 端（旁观者 + 降级递补者）下发的 prefs **不含 `osc52` 键**（即使全局 --osc52 开启）；rw 端按全局下发；升格 Welcome 携 rw 档（P5-6 时序纪律）。
- **前端契约（一行）**：`prefs.osc52 === true` 才加载 ClipboardAddon（04 契约不变）+ **一次性门闩**（`osc52Loaded` 模块级 flag）——升格 Welcome 重放 prefs 时防 ClipboardAddon 二次加载（双写剪贴板虽同值无害，但重复注册 OSC52 handler 是无谓面）。ro 端永远收不到 `osc52:true` → 永不加载（D-13 的前端自然落点，无需 ro 特判代码）。

## Multi-Client First-Screen & Title Boundary (D-11/D-12)

- **新客首屏（D-11）**：服务端 attach 完成时向 PTY 前台进程组显式 SIGWINCH 强制全屏程序重绘——**前端零改动**（重绘输出走既有 OUTPUT 扇出流入）。行内 shell 下次输出自然追上。
- **标题（D-12 终局）**：纯前端解析不变（04-UI-SPEC §Title Sync Contract 逐字有效）；新客标题随 SIGWINCH 重绘/下次 OSC 2 自然恢复；'T' TITLE 帧终局不实现。服务端 OUTPUT 零拷贝不跑 OSC 状态机（非本契约范围）。
- **min-rect 渲染推论（D-09）**：任何客户端窗口 ≥ PTY 尺寸，各端按自己窗口渲染、多余面积留白——**无 S→C 尺寸下发帧，前端零适配**；纯 ro 会话旁观者运行期窗口缩放不上报（ro 不发 RESIZE 的直接结果），缩到小于 PTY 尺寸者看到裁剪画面、重新 attach 恢复——README 明示（文档职责，非 UI）。
